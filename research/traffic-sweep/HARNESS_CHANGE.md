## 1. What the change is

- **A second epoch, not an edit of the frozen one.** `execution/candidate_sweep.py` (new) compiles
  `hotel-traffic-sweep-v1`. The frozen `candidate_pilot.py`, its descriptor and `runtime-policy.json` are
  byte-identical to `e4fd4c7`. A test checks each against `git show e4fd4c7:<path>`.
- **Selector.** The epoch is active only when a committed file `modules/hotel-reservation/execution/study-epoch.json`
  contains `{"schemaVersion": 1, "studyEpoch": "hotel-traffic-sweep-v1"}`. With no selector the runtime is the frozen
  epoch: `STUDY_EPOCH`, `CELL_COUNT = 80`, the budget 18000 / 17700, the same 22 `CONTROLLER_PATHS` keys, and an
  embedded launcher whose sha256 is unchanged (`e86e3cb3...`). With the selector present, `CONTROLLER_PATHS` swaps in
  the sweep compiler, descriptor and policy. It also adds three digest-bound entries: `frozen-compiler`,
  `protocol-gates` and `study-epoch-selector`. A selector naming any other value refuses to load. Committing the
  selector is a framework commit, so every gate sentence is re-derived.
  **The selector is not created**: committing it is the activation step and belongs to the user.
- **Per-cell plan values.** Each compiled sweep cell carries a `timing` block: rate, inter-arrival, concurrency,
  request timeout, warm-up seconds and rate, measurement, offered, onset (base, seeded offset, effective), hold, scored
  window, per-phase witnessed-start floors, TCP snapshot offsets, Jaeger window, minimum system samples, join slack,
  and two capture flags. The cell contract copies it. `candidate_runtime.cell_timing(contract)` is the only reader.
  A frozen contract has no `timing`, so it returns the frozen compiler's constants plus the literals the runner and
  validator held at `e4fd4c7`. A sweep contract's timing must equal the active compiled plan's timing for that run ID
  byte for byte, so a retained contract cannot bring its own numbers.
- **Plan (defaults)**: rates 10, 1, 0.2, 0.05 /s. Warm-up 30 s at the cell's rate. Measurement 180 s. Onset 60 s plus
  a seeded per-cell phase offset in [0, 1/rate). Hold 60 s. Regimes no-fault-calibration, search-pause,
  profile-cpu-throttle, rate-net-delay (100 ms). Posture `full` only. 4 blocks; each block holds every
  (regime, rate) pair once. That is 4 × 4 × 4 = **64 cells**, and offered = rate × 180 s = 1800 / 180 / 36 / 9.
  Order within a block is a Fisher-Yates shuffle with SHA-256 draws from seed `20261003`; the seed and every block's
  run-ID order are in the descriptor. Digests: descriptor `c79d5ff0...05b2`, plan `e6e0aadd...ce68`. Both are
  identical under `/usr/bin/python3 -I` (3.9.6) and `uv run` (3.13); see the 3.9 test.
- **Run IDs** `<regime>-r<rate token>-b<NN>-full-a01`, for example `search-pause-effect-r0p05-b01-full-a01`. The
  workload regex is generic in regime, rate, block and posture; the frozen regex pinned posture membership, the guard
  class that stopped Hotel #6. Membership is proven by the byte-exact contract comparison against the admitted plan.
  The workload refuses any rate other than the one encoded in the run ID.
- **Wall budget, derived**: cell period = 30 warm-up + 5 barrier + 180 measurement + 60 overhead = 275 s. Then
  64 × 275 + 600 prepare + 300 cleanup = 18,500 s, rounded up to whole hours = **21,600 s (6 h)**, and the minimum
  remaining at first mutation is 21,300 s. The 60 s overhead is an engineering default; the measured figure is in §7.

## 4. Coordinator findings (2026-10-03)

1. `candidate_search.py:157` fixed the duration at 120 s. **Implemented**: §3 row 3.
2. `MINIMUM_PHASE_STARTS = 100` rejects 0.2 /s and 0.05 /s. **Implemented**, and the first derivation was itself
   wrong. A floor of `need(rate, nominal phase seconds)` gives 2 at 0.05 /s for every onset offset below 20 s.
   For offsets in [18.7, 20) s, only one request is scheduled after recovery, so that floor would fail by construction
   (about 1 in 15 such cells). The floor is now `max(1, ceil(FLOOR × the plan's own slots in the phase))`. "Pre" is the
   slots before onset, "during" the slots in [onset, onset + hold), and "post-readiness" the slots from
   onset + hold + 2 s. A phase with no scheduled slot is refused at compile time. FLOOR = 0.5 is taken from the vendored
   gates.
3. Seeded onset phase. **Implemented**. Without it, 60 s is a multiple of every inter-arrival: every onset falls on a
   scheduled request, so time to detection at low rate would be set by the plan. The test
   `test_without_the_onset_offset_every_low_rate_onset_falls_on_a_scheduled_request` shows this. The offset is
   `sha256(seed, epoch, runId, "onset-phase")` mapped to [0, 1/rate) and recorded per cell
   (`faultOnsetPhaseOffsetSeconds`). Each rate has 16 distinct offsets (test). No-fault cells carry the same seeded
   pseudo window. `ONSET_PHASE_OFFSET = "none"` restores the bare 60 s.
4. `docker compose logs --timestamps`. **Implemented**, sweep cells only. Both log parsers locate their marker
   anywhere in the line; the sealed-cell test uses prefixed lines. Any analysis code reading `application.log` must
   accept the `<service>-1  | <RFC3339Nano> ` prefix.
5. Full trace store. **Implemented as a de-duplicated remainder**, sweep cells only. The frontend query stays the
   scored capture, unchanged. Then each of the other nine application services is queried for the same window. Only
   traces absent from the frontend capture are kept, in `jaeger-raw-remainder.json`, with every service's `traceCount`.
   The union is the store for those ten services. Storing every service's full response would be about 10 × the 27 MB
   frontend file (sel1 cell, measured) per 10 /s cell. The terminal checks the header, the window, the per-query limit
   and that no trace repeats. The remainder is not scored.

## 5. Protocol gates and evidence integrity

- Vendored byte-identically. The measurement repo's `test_vendored_copy_is_byte_identical` now runs for this copy
  (it was skipped) and passes. `test_hotel_traffic_sweep.py` repeats the byte check.
- For sweep cells the terminal builds the normalised cell from the GATES.md mapping table: barrier = 0; scheduled =
  `scheduledMonotonicOffsetSeconds`; started / ended = actual − barrier; status `ok` iff completed and 200,
  `timeout` iff the error says "timed out", else `failed`. The fault stamps map as `startedMonotonic` → onset issued
  (pre-command), `appliedMonotonic` → onset returned (an upper bound), `revertingMonotonic` → revert issued,
  `unpausedAtMonotonic` / `revertedAtMonotonic` → revert returned. The plan's offered, rate and window come from the
  compiled timing; the profile rate is the retained opportunity plan's rate.
- **Corrected after review: G4 cannot fail inside `validate_cell`.** Every G4 input is already enforced before it
  runs, or is a constant: the ledger row count (`validate_ledger`), plan rate == timing rate, `valid: True`, and
  `ledgerKind`. F1's `onsetCommandBounded` is a constant as well, because the mapping sets `onsetSource =
  "pre-command"` (true of both adapters' code, not observed per cell). G4 is therefore a **recorded** check here, not
  an independent guard; F1's other checks, G1 and G2 can fail on a healthy-looking cell, and the tests show that.
- Blocking: F1 on fault cells, G1, G2 and G4. Any non-pass raises `TerminalError`, the cell is blocked, and the runtime
  stops on the first invalid cell. R2.recovery is recorded and never blocks. **P0, R1 and R2 are not evaluated**: the
  harness writes none of their inputs (connection counts, per-channel counts, per-route readiness). G4's channel scope
  is ledger-only (`channels: {}`), and its ledger share is ~1.0 by construction. That is weaker than GATES.md intends;
  see Q6.
- The existing integrity checks all still run first: hash-chained ledger replay, plan replay, witness bijection,
  manifest, provenance, posture, cleanup, nuisance and docker events.
- Ledger: per-request scheduled / started / ended / outcome are unchanged (`_ledger_record`, `LEDGER_KEYS`).
- F-ADH-085: in both adapters `startedMonotonic` is stamped immediately before the command
  (`faults/compose_pause.py:155-157`, `faults/lmt_faults.py` before `_apply`). The witness bounds it to
  [onset − 0.05, onset + 2.0] s of the cell's schedule. It also requires started ≤ applied < reverting. F1 adds
  |issued − schedule| ≤ 1.0 s. Measured lateness over the 128 retained fault receipts of sel1 and lmt2 is
  0.154–0.224 s (command in §7). Tests plant an early stamp, a late stamp, a post-command stamp and a 1.5 s late
  onset; each is rejected.

## 7. Cell duration, and how to check it

- Measured on the frozen epoch: the sel1 and lmt2 journals (`tmp/hotel{sel1,lmt2}-evidence/x/runtime-journal.jsonl`,
  `recordedAt` differences, 79 intervals each) give a median of 184.6 / 184.4 s and a maximum of 191.8 s per cell,
  against 155 s timed. That is about 30 s of overhead, 37 s at most. Instance, srv4.
- Estimate for the sweep, using the same overhead plus 0–20 s for the remainder queries (about 0 at low rate):
  215 s timed, so **≈ 245–270 s per cell**, and 64 cells ≈ 15,700–17,300 s = **4.4–4.8 h** (`?` until the first
  cells run). The declaration's "~5 min / ~5.5 h" is an upper bound. The budget assumes 275 s per cell (6 h window).
- A DRY_RUN stops before the first mutation, so **it cannot measure a cell**. What it can show:
  `uv run python modules/hotel-reservation/execution/candidate_sweep.py` prints runCount 64, maximumWallSeconds 21600
  and the plan digest; the launcher's plan-pin and runCount checks pass; `CONFIG.run_window_hours` prints 6. The cell
  period is first observable as the gap between the first two `runtime-journal.jsonl` `recordedAt` stamps after
  launch.
- Command used for the lateness figure in §5: a `uv run python` loop over
  `tmp/hotel{sel1,lmt2}-evidence/x/runs/effect/*/b*/*/attempt-01/fault-receipt.json`, computing
  `startedMonotonic − plan.barrierMonotonic − 45`.

## 9. Open questions for the user (preregistration-class unless marked)

1. **Rates** 10, 1, 0.2, 0.05 /s. At 0.05 /s a cell has 9 requests, and the pre / during / post floors are 2 / 2 / 1
